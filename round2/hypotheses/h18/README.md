# H18 — Project Ontology is a meaningful executable second domain

## Claim

The same generic EOO mechanisms can govern the real hypothesis-driven lifecycle of operational-ontology-poc, enforce preregistration/evidence/verdict invariants, and provide at least one operational advantage over file-only discipline without replacing Git as authority.

## Strong null/rival

Project Ontology merely mirrors Markdown/JSON and requires equally bespoke validators/actions, adding no operational value beyond conventional repository scripts.

## Why this exists

Representing research entities, links, states and governed actions in the shared EOO should allow generic lifecycle enforcement, provenance queries and generated action surfaces already needed by other domains.

## Primary falsifiers

- Project lifecycle enforcement requires bespoke runtime branches.
- A supported/rejected verdict can be set arbitrarily without evaluator evidence.
- Project Ontology cannot prevent or surface a preregistered illegal transition.
- The equally strong file-only baseline achieves the same generated/query/action behavior with no greater bespoke change and lower recurring complexity across all measured task classes.

## Python Hypothesis role

RuleBasedStateMachine generates hypothesis lifecycle operations, stale edits, evidence binding errors, verdict attempts and supersession sequences.

## Stop rule

- If self-hosting requires Project-specific Engine code, reject/narrow before adding more project features.
